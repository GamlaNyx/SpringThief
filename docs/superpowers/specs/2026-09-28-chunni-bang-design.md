# 春泥棒：NFT《春》失窃案设计文档

## 1. 文档信息

- **题目名称**：春泥棒
- **题目类型**：招新趣味赛第一题，网页交互式取证/解谜题
- **目标玩家**：没有区块链或密码学基础的新生、网络安全兴趣初学者
- **预计用时**：单人 10–20 分钟
- **文档状态**：设计已确认，进入实现准备
- **核心知识点**：助记词、种子、私钥、地址，以及 BIP-39、BIP-32/BIP-44、secp256k1、Keccak-256 的基本关系

## 2. 背景故事

工作室钱包中名为《春》的 NFT 被偷走了。小偷没有留下真实身份，只在工作室的电脑中留下了一套伪装成日常文件、网页、小游戏和加密便签的线索。

玩家需要进入模拟的工作室桌面，调查四组线索，找出 12 个按顺序排列的助记词。恢复台会逐步解释：助记词可以还原钱包种子，种子可以派生私钥，私钥最终对应一个区块链地址。玩家解锁计算工具后，提交正确的私钥和地址，找回 NFT《春》。

题名“春泥棒”取自同名日语歌曲，作为彩蛋存在；题面主线只围绕 NFT《春》的失窃和钱包恢复展开，不要求玩家了解歌曲背景。

## 3. 设计目标与非目标

### 3.1 设计目标

1. 让完全不了解钱包的玩家能在明确提示下完成第一题。
2. 让玩家通过实际操作理解“助记词 → 私钥 → 地址”的方向关系。
3. 让四种线索形态各有特色：文件、搜索、小游戏、低门槛解密。
4. 让玩家在解题过程中产生主动搜索和继续了解算法的兴趣。
5. 题目数据可替换，后续可以快速更换词语、线索和故事。

### 3.2 非目标

- 不要求玩家手算密码学大整数或实现加密算法。
- 不连接真实钱包、真实 NFT 或任何有价值的链上资产。
- 不依赖真实互联网才能完成主线；浏览器模块使用题内模拟搜索数据。
- 不把专业术语记忆作为唯一难点；每个术语都配有可读的解释和渐进提示。

## 4. 玩家流程

1. 进入“工作室桌面”，阅读案件摘要和目标：找回 NFT《春》。
2. 打开档案室，取得第一组 3 个词及位置线索。
3. 打开模拟浏览器，按照搜索目标找到第二组 3 个词。
4. 打开游戏中心，完成记忆配对、拖拽排序、找不同，取得第三组 3 个词。
5. 打开解密终端，依次完成凯撒移位、键盘错位、摩斯密码，取得第四组 3 个词。
6. 在线索背包中把 12 个词放入第 1–12 位。
7. 打开钱包恢复台，阅读关系图并依次输入正确的标准/算法名称。
8. 工具在本地完成真实派生，玩家复制并提交私钥和地址。
9. 验证成功后按题目配置执行 flag 派生，显示案件结案、NFT《春》找回，以及简短知识回顾。

页面始终显示进度、已获得词语数量和“推荐下一步”。玩家可以自由打开已解锁模块，但不会因为自由探索而失去主线。

## 5. 页面与模块设计

### 5.1 工作室桌面

桌面模拟一台工作室电脑，包含以下图标：

- 档案室
- 浏览器
- 游戏中心
- 解密终端
- 钱包恢复台
- 线索背包
- 帮助/知识库

首次进入时只突出档案室和案件摘要。完成一个模块后，桌面通过通知提示下一步，但不强制玩家按固定顺序操作。

### 5.2 档案室：第一组

档案室直接提供第一组 3 个词。线索载体可以是失窃报告、打印便签、文件命名或照片元数据的视觉模拟。

要求：

- 词语本身清晰可读，不在第一组设置高难度。
- 每个词必须同时给出第几位，或给出玩家能推导出唯一位置的简单提示。
- 完成后写入线索背包，并显示“第 1 组已完成”。

### 5.3 模拟浏览器：第二组

第二组固定为（槽位直接给出）：

`fever / dream / high`

搜索引导来自 Taylor Swift《Cruel Summer》的开头歌词前三个单词。题目页面只给出搜索目标和必要的作品信息，不直接粘贴整句歌词；玩家在题内模拟搜索页面中完成查找。

模拟浏览器要求：

- 预置一个可搜索的静态页面索引，默认不访问外网。
- 搜索结果中既有正确页面，也有少量干扰结果。
- 正确结果提供 3 个词和对应位置线索。
- 搜索框支持关键词搜索和回车提交，错误搜索给出“没有找到相关档案”，不直接显示答案。
- 后续出题人可以替换搜索词、页面标题和答案，不需要修改桌面逻辑。

### 5.4 游戏中心：第三组

三个小游戏各产生 1 个词：

1. **记忆配对**：翻开卡片，配对“物品—标签”；全部配对后显示一个词和位置。
2. **拖拽排序**：把春季物件按页面给出的轻量规则排序；顺序正确后显示一个词和位置。
3. **找不同**：在两张简化图片或图标网格中找到一个差异；点击正确位置后显示一个词和位置。

三个小游戏共享统一的游戏机外壳，均具备：

- 开始前的单句目标说明；
- 明确的成功/失败反馈；
- 失败后可立即重试；
- 不超过两次操作规则解释；
- 完成后只奖励当前词，不自动暴露其他词。

### 5.5 解密终端：第四组

三个解密工具各产生 1 个词：

1. **凯撒移位**：给出字母表和一条示例，玩家调整位移量并解出文本。
2. **键盘错位**：展示一段按相邻键误输入的文本，玩家依据屏幕键盘还原原文。
3. **摩斯密码**：提供点划符号、字母表对照和输入框，玩家逐组翻译文本。

终端采用“看例子—尝试—获得提示”的节奏，不要求玩家知道密码学历史。提示分三级：

- 方向提示：告诉玩家应观察位移、键盘邻键或点划组合；
- 操作提示：指出页面上的对应控件；
- 关键提示：给出下一步转换方式，但不直接填入答案。

### 5.6 线索背包

线索背包展示四组线索和当前收集进度：

- 词语文本
- 来源模块
- 推断出的槽位（1–12）或位置线索
- 是否已确认

背包不自动替玩家排好最终顺序。玩家需要在恢复台完成一次明确的拖拽或点击排序。

### 5.7 钱包恢复台

恢复台分为三段，每段都必须先输入正确的名称才能使用工具：

1. **助记词 → 种子**：接受 `BIP-39` 或 `BIP39`。
2. **种子 → 派生私钥**：接受 `BIP-32`、`BIP32`、`BIP-44` 或 `BIP44`；页面说明本题采用 Ethereum 的 BIP-44 路径。
3. **私钥 → 地址**：接受 `secp256k1` 与 `Keccak-256`；允许玩家分两次填写，也允许输入页面给出的组合名称。

每一段包含：

- 输入框和解锁按钮；
- 关系图中的当前高亮箭头；
- 可展开的术语解释；
- 分级提示按钮；
- 解锁后的本地计算结果和复制按钮。

网页真实执行以下流程：

```text
12-word BIP-39 mnemonic
        ↓ PBKDF2-HMAC-SHA512（由 BIP-39 规定）
seed
        ↓ BIP-32 hierarchical derivation
Ethereum account at m/44'/60'/0'/0/0
        ↓ secp256k1 public key + Keccak-256
Ethereum address
```

玩家不需要手算上述过程，但必须理解步骤顺序、输入算法名称、复制结果并提交私钥和地址。

## 6. 助记词与题目数据约束

### 6.1 固定内容

- 每组 3 个词，共 12 个词。
- 第一组：`only / sunny / day`。
- 第二组：`fever / dream / high`，通过模拟浏览器引导玩家搜索 Taylor Swift《Cruel Summer》开头歌词的前三个单词，槽位直接展示。
- 第三组：`forever / night / day`。
- 第四组：`your / how / good`。
- 四组在最终题目配置中对应 1–12 的固定槽位；实现时不得因为模块展示顺序而改变词序。

### 6.2 BIP-39 有效性

若恢复台采用真实 BIP-39 模式，12 个词必须来自 BIP-39 英文词表，并通过 12-word mnemonic 的校验和验证。不能只根据语义拼接 12 个词。当前固定展示词组必须在实现阶段用标准库实际验证；若验证失败，必须在不伪称其为有效 BIP-39 的前提下，增加明确的校验词/校验层，或将恢复台切换为题目说明中的教学化 B 模式。

出题数据生成流程：

1. 先确定四组词和最终槽位。
2. 使用 BIP-39 校验函数验证整组助记词。
3. 如校验不通过，调整未锁定词或词序，直到得到唯一有效组合。
4. 使用固定派生路径生成预期私钥和地址。
5. 将最终答案写入本地题目配置，并在构建时运行一致性检查。

题目配置中的中间数据不应直接包含 flag 明文。只要判题逻辑完全在前端，玩家仍可能通过开发者工具查看计算过程；因此 flag 必须通过下面的派生流程生成，而不是以明文常量存储。若后续用于正式竞赛，应将最终校验迁移到服务端。

## 6.3 Flag 派生方案

目标 flag 为：

`DLNUFCG{w3lc0m3_t0_w3b3}`

实现提供两种可选方案，二选一即可；两种方案都不把 flag 明文放入前端静态资源。

### 方案一：加密隐藏

1. 使用由题目组预先生成的测试私钥、地址或固定盐值作为密钥材料。
2. 将 flag 使用明确记录在设计配置中的对称加密方案加密，例如 AES-GCM。
3. 前端只保存密文、随机 nonce、认证标签和解密所需的派生参数。
4. 玩家提交正确地址后，页面使用本地计算出的结果派生解密密钥并尝试解密。
5. 解密成功后显示 flag。

注意：纯前端加密只能隐藏源码中的明文，不能抵抗认真逆向；它的目标是避免直接搜索到 flag，而不是提供竞赛级密钥保护。

### 方案二：预计算数据与地址异或

1. 题目组预先计算一段与 flag 等长的 `data`。当前 flag 是 24 个 UTF-8 ASCII 字节，因此 `data` 必须是 24 字节、48 个十六进制字符。
2. 将 Ethereum 地址规范化为 20 字节，并按约定编码为可重复使用的字节序列（去掉 `0x` 后解析为十六进制字节）。
3. 对 `data` 与循环重复的地址字节执行异或，得到 flag 的 UTF-8 字节；形式化表示为 `flag[i] = data[i] XOR addressBytes[i mod 20]`。
4. 前端只保存 `data` 和异或规则；玩家算出正确地址后，页面执行同样的异或并进行 UTF-8 解码。
5. 解码结果必须严格匹配 `DLNUFCG{w3lc0m3_t0_w3b3}`，否则显示“地址仍不正确”。

异或方案必须在配置中明确：字节编码、地址是否去除 `0x`、短数据是否循环、结果长度和 UTF-8 解码方式。不能依赖 JavaScript 字符串逐字符异或。

## 7. 状态与数据结构

建议使用单页应用的集中状态管理，所有题目内容放在配置对象中，示例结构如下：

```ts
type Clue = {
  id: string;
  group: 1 | 2 | 3 | 4;
  word: string;
  slot: number;
  source: string;
  hints: string[];
};

type ChallengeConfig = {
  title: string;
  nftName: string;
  clues: Clue[];
  browserIndex: SearchRecord[];
  gameDefinitions: GameDefinition[];
  cipherDefinitions: CipherDefinition[];
  mnemonic: string;
  derivationPath: string;
  expectedPrivateKey: string;
  expectedAddress: string;
  flagMode: 'aes-gcm' | 'xor-address';
  flagPayload: string;
  flagNonce?: string;
  flagAuthTag?: string;
};
```

实现时不应把最终答案散落在各个组件中。模块只负责发放线索和记录完成状态；恢复台负责校验顺序、解锁算法、计算和最终提交。

## 8. 判题、错误处理与提示

### 8.1 判题顺序

1. 检查是否收集满 12 个词。
2. 检查词语是否为有效 BIP-39 助记词。
3. 检查槽位顺序是否正确。
4. 检查算法名称是否匹配当前步骤。
5. 检查私钥格式和数值是否正确。
6. 检查地址是否正确且与目标账户匹配。

### 8.2 错误反馈

- 词语缺失：提示还缺少哪一组线索，不显示答案。
- BIP-39 无效：提示“这组词无法组成有效助记词，请检查顺序或拼写”。
- 算法名称错误：提示“工具还没有识别这个名称”，并提供术语资料入口。
- 私钥错误：提示格式或内容不匹配，不泄露正确值。
- 地址错误：提示“地址与当前私钥不匹配”，允许重新复制。

输入比较前统一做安全的格式规范化：助记词按空白折叠并转小写，算法名称忽略大小写、空格和连字符差异，私钥和地址按十六进制格式校验；不得为了“方便”在比较时截断私钥或地址。

### 8.3 提示系统

每个模块最多三次提示，默认顺序为方向、操作、关键。提示可记录在本地状态中，用于赛后统计卡点；提示不改变正确答案。

## 9. 安全与隐私边界

- 全部计算在浏览器本地完成，不上传助记词、私钥或答案。
- 使用专门生成的测试助记词，钱包中不放真实资产。
- 页面明确标注“本题私钥仅用于练习，禁止用于真实钱包”。
- 不接入浏览器钱包扩展，不请求签名，不发送交易。
- 生产构建中不得把真实项目钱包或真实 NFT 信息作为题目数据。
- 前端答案可被查看这一点必须写入出题说明；需要防作弊时改用服务端最终判题。

## 10. 建议实现方式

- 采用 Vite + React + TypeScript 的单页应用结构，桌面、模块窗口、线索背包和恢复台共享状态。
- 使用 `ethers` v6 或同等级本地库完成 BIP-39 助记词解析、HD 派生和 Ethereum 地址计算。
- 所有浏览器页面、文件、游戏和解密题均使用本地静态数据。
- 将桌面窗口、提示条、输入校验、进度显示做成可复用组件。
- 为每个小游戏、每种密码和恢复台步骤提供独立函数，便于单元测试。

## 11. 验收标准

### 11.1 玩家体验

- 没有钱包基础的玩家能通过页面提示理解三者关系。
- 首次完成用时目标为 10–20 分钟。
- 四个线索模块都能独立完成并给出清晰反馈。
- 至少一次搜索行为和至少一种解密操作由玩家主动完成。
- 玩家能说出：助记词用于恢复钱包，私钥用于控制账户，地址用于标识账户。

### 11.2 技术正确性

- 最终 12 词通过 BIP-39 校验。
- 使用固定路径得到唯一预期私钥和地址。
- 恢复台拒绝错误顺序、错误算法名称、错误私钥和错误地址。
- 刷新页面后，题目状态按照预期恢复或明确重置。
- 全流程无需外网，无真实链上交互。

### 11.3 题目可维护性

- 第二组搜索数据可通过配置替换。
- 四组词、位置、提示、小游戏参数和密码题文本不依赖组件内部硬编码。
- 修改题目答案后，可以通过自动校验重新生成预期私钥和地址。
